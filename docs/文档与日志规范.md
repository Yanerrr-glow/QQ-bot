# 文档与日志规范

本规范用于保持项目入口清楚、运行日志可排查、历史记录不冒充当前行为。目录调整时先更新本文件和根 README 的目录导览；不因整理而搬动仍被脚本或部署配置引用的路径。

## 文档放哪里

| 内容 | 位置 | 写什么 |
|---|---|---|
| 项目入口与基本说明 | 根目录 `README.md` | 项目用途、最短启动路径、目录概览、安全提示和文档入口；不承载长篇技术细节 |
| 详细手册与持续开发记录 | `docs/开发日志.md` | 架构、运行机制、配置细节、历史决策索引；开发记录按日期倒序追加 |
| 专题说明与方案 | `docs/主题_YYYY-MM-DD.md` | 单一主题的背景、证据、方案、决定、限制和后续事项 |
| 规范与历史材料 | `docs/` 下对应专题或 `docs/人设历史/` | 长期有效的维护规则与只供参考/恢复的旧材料 |
| 子系统使用和开发说明 | 对应子目录 `README.md` | 只讲该组件自己的安装、调用、边界和扩展方式 |
| **人格文件的内容规范** | `docs/人格包内容规范.md` | 三层分工、各文件的格式硬规则、写作要求、改名与新增铁律的配套动作。**规范里带「判据」的条目必须同时有检查脚本**（`验证/_人格包检查.py`），否则规范会与代码漂移 |
| 部署步骤 | `deploy/README.md` | 服务器准备、部署、升级、运维和部署侧排错 |
| 运行时状态和诊断输出 | `data/` 或组件配置的数据目录 | 机器生成的当前运行信息；不作为开发决策记录 |

### README 维护

- 根 README 只回答“这是什么、怎么开始、接下来去哪看”；长篇说明放入 `docs/` 或对应子系统文档。
- 只记录当前仍成立的行为。历史方案标注日期和状态，并链接到 `docs/` 内的专题记录；已移除的能力不可继续写成可用功能。
- 目录树只列主要入口和边界，不抄录每个模块的实现说明；改目录或职责时同步更新。
- 命令注明执行目录、运行环境和必要前提。示例不得包含真实密钥、账号凭据或个人数据。
- 合并或迁出章节后，检查文档地图、标题锚点和相对链接；不要留下指向不存在文件的链接。

## 开发记录格式

需要保留决策依据、踩坑或跨版本变化时，在 `docs/` 新建简短主题文件，文件名使用主题加 ISO 日期，例如 `docs/日志治理_2026-10-02.md`。持续性开发记录追加到 `docs/开发日志.md`，按日期倒序；不要在根 README 累积历史细节，也不要只靠目录或链接假装旧记录仍存在。

每个记录以日期标题开头，按需包含以下信息：

```markdown
## YYYY-MM-DD：简短主题

- 背景：遇到什么现象，影响谁或什么流程。
- 判断：依据是什么；哪些是已验证事实，哪些仍是假设。
- 改动：改了哪些路径或约定，为什么这样改。
- 验收：检查了什么、结果如何；未检查的事项明确写出。
- 回退/后续：必要时写恢复方式、已知限制或下一步。
```

每条只描述一个主题；用日期、路径和可复核证据定位，不粘贴大段终端输出。日志、聊天记录、密钥和真实用户标识不得复制进开发记录。需要引用运行数据时先脱敏并只保留必要片段。

## 运行日志规范

### 归属与位置

| 运行场景 | 默认查看位置 | 说明 |
|---|---|---|
| Windows 机器人 | `data/runtime/logs/bot.log` 与启动窗口 | 启动脚本将 UTF-8 控制台输出追加到文件；窗口可用于观察实时输出 |
| Docker 部署 | `docker compose logs -f bot`（在 `deploy/`） | 容器日志走 stdout/stderr；持久数据仍在挂载的 `data/` |
| 桌面控制台 | `.console/data/` | 连接目标和令牌等配置与诊断数据分开放置；令牌不得写入日志 |
| 离线验证 | `验证/` 对应脚本的输出，必要时将简要验收记录追加到 `docs/开发日志.md` | 临时输出不留在源码目录；保存时注明脚本、日期和结果 |

运行日志是诊断材料，不是开发日志。运行日志和聊天数据都可能含个人信息，默认不提交、不导出、不贴到 issue；确需留档时先脱敏、限定范围并注明保留期限。`data/` 下的数据库、聊天记录和日志不可作为清理目录随意删除。

### 格式与级别

- 文本日志统一 UTF-8；每条记录一行，时间使用带时区的 ISO 8601 时间，或明确标注本地时区。跨组件排查优先使用同一时区。
- Python 日志使用标准 `logging`，格式为 `时间 [级别] logger | 消息`。桌面端继续经过 `RedactingFilter`；机器人标准 logging 必须接入已配置的输出 handler。
- `DEBUG` 用于临时诊断且默认关闭；`INFO` 记录启动、连接、任务结果和状态变化；`WARNING` 记录可恢复异常或退化；`ERROR` 记录当前操作失败；避免把正常轮询写成高频日志。
- 记录事件、对象类型/内部短 ID、结果和耗时等排查所需上下文；异常保留一次完整 traceback。不要记录 API Key、令牌、Cookie、认证头、完整环境变量、原始私聊/群聊内容或不必要的文件正文。
- 用户可复制或外发的日志在写出前脱敏。不要用“删掉密钥参数”的不完整正则代替统一脱敏出口；新增日志字段时同步检查过滤器和展示路径。
- 长期运行日志必须有大小/保留策略，不能无限增长。轮转或清理不得误删 `memory.db`、聊天记录、状态文件等业务数据。

### 排查顺序

1. 记下故障发生时间及所在时区、机器人是否仍在运行、影响范围。
2. 先确认日志通路正常，再搜索与时间相邻的启动、连接、请求、任务和异常记录；日志全空时先查 handler、启动脚本重定向和容器输出。
3. 从最靠近故障的组件逐层检查：Windows 看 `data/runtime/logs/bot.log`；Docker 看 `docker compose logs -f bot`；桌面端看 `.console/data/`。
4. 开发记录写结论、复现条件、证据位置和实际修改，不把整份运行日志复制进去。

## 目录整理边界

- `plugins/` 是机器人运行插件；`desktop/plugins/` 是桌面 UI 插件，两者职责不同，不合并。
- `验证/` 是可复现的验证入口；临时缓存（如 `__pycache__/`）不是源文件，不纳入文档目录树。
- `.venv*`、`.pip-tmp`、`.work-tmp` 是本机环境或临时目录；`.console/` 是本机控制台数据；`dist/` 是打包产物；`data/` 是运行状态。它们不属于源代码层级。
- `_工具链/` 收项目专用启动、维护和发布脚本。通用机制放工作区 `可复用工具链/`，不要复制进项目。

## 源码、人设与运行数据

### 目录职责

| 路径 | 内容 | 维护规则 |
|---|---|---|
| 根目录 `bot.py` | 应用入口与插件加载 | 只保留启动编排；业务逻辑放入对应插件模块 |
| `plugins/ai_chat/` | QQ 机器人业务插件 | 按会话、人格、记忆、外部访问等职责维护；模块索引见 [`plugins/ai_chat/README.md`](../plugins/ai_chat/README.md) |
| `desktop/` | 独立桌面管理端 | 保持与 NoneBot 插件分离；管理端插件继续放 `desktop/plugins/` |
| `persona/_registry.json` | 默认激活哪个包（跟镜像走的部署期默认值） | 人工可改；运行时切换会写这里，但**以 `data/runtime/persona/_active` 为准** |
| `persona/packs/<包>/` | 一个人格包 = 一个角色需要的全部静态文件 | 静态部署资产；用户维护底层和禁止事项，表层文件只用于首次播种；`_pack.json` 声明身份元数据 |
| `persona/_TEMPLATE/` | 新建人格的脚手架 | `_` 前缀 = **不参与扫描**，不会被当成可切过去的人格 |
| `persona/active/` | 包化**之前**的那一份原样副本 | 只作回退材料（`AI_CHAT_PERSONA_*_FILE` 显式指回它才生效）；不参与导出，确认线上跑包之后可整体删除 |
| `docs/人设历史/` | 历史迁移对照与分层前备份 | 仅作历史参考和恢复依据；不得当作运行时加载文件 |
| `data/runtime/` | 机器人运行时持久化数据 | 挂载卷中的唯一运行数据根；由 `AI_CHAT_LOG_DIR` 指定 |
| `data/runtime/persona/<包>/` | 当前包的运行数据：表层、候选池、信号账本、审计、评估 | 由人格模块写入，**按包隔离**；和 `persona/packs/<包>/` 的只读模板分开 |
| `data/runtime/logs/` | 机器人文件日志 | 追加诊断输出；容器默认仍写 stdout/stderr |
| `.console/` | 桌面控制台本机配置、凭据和诊断数据 | 与机器人 `data/` 分开；不得放入机器人数据卷 |

当前路径已经统一到 `persona/packs/<包>/` 与 `data/runtime/`。Docker `COPY`、部署上传、启动脚本、自检、维护脚本和发布导出均按新路径工作。**包化（2026-10）之后又加了一层按包隔离**：运行数据落在 `data/runtime/persona/<包>/`，旧版平铺的那一份由 `packs.migrate_layout()` 在启动时归位（幂等，迁移前先复制一份到 `data/runtime/_backup_<日期>_人格包迁移/`；目标重名时改名为 `.legacy` 并记 error，不覆盖任何一边）。旧版 `AI_CHAT_LOG_DIR=data` 会在启动时将旧目录内容迁入 `data/runtime/`；迁移前后都应确认没有旧版机器人进程仍在写旧目录。

### 人格文件的唯一写入源

| 数据 | 唯一权威位置 | 写入者 | 维护要求 |
|---|---|---|---|
| 身份元数据 | `persona/packs/<包>/_pack.json` | 项目所有者/维护者 | `bot_name` 必须与 `base.txt` 里的角色名逐字一致；`master_title` 留空 = 不干预 |
| 底层人格、禁止事项、特质注册表 | `persona/packs/<包>/base.txt`、`forbidden.txt`、`traits.json` | 项目所有者/维护者 | 人工修改并复核相互一致；自动迭代不得写这三份源文件 |
| 表层人格模板 | `persona/packs/<包>/surface.txt` | 项目所有者/维护者 | 新部署的播种模板；已有运行实例的更改应按其运行数据迁移，不假设模板会覆盖旧副本 |
| 当前表层人格 | `data/runtime/persona/<包>/surface.txt` | 通过校验和冲突闸门的表层更新流程 | 不直接把包模板复制覆盖到现有运行数据；应保留变更记录和撤回路径 |
| 人格自动变更审计 | `data/runtime/persona/<包>/changelog.json` | 人格管理代码 | 仅作为审计记录，不反向覆盖人格源文件 |
| 当前激活的包 | `data/runtime/persona/_active`（运行时）／`persona/_registry.json`（默认） | `config.switch_persona()` | 切换是**热切换**：写标记 + 清缓存 + 同步身份；三层正文每轮现读，不用重启 |

人工编辑人格文本时使用 UTF-8、保留清晰标题与短规则；每条规则表达一个约束或行为，不把相互矛盾的规则分散写在不同层。编辑后检查来源、所属层级和闸门登记；私人对话原文不得写进公开的人格元数据。

### `data/` 写入分类

| 类别 | 常见路径 | 写入与恢复边界 |
|---|---|---|
| 消息历史 | `data/runtime/chatlog_*.json`、`chatlog_*.archive.jsonl` | 机器人追加/整理；内容敏感，保留原始归档，手工清空前确认已备份 |
| 长期记忆 | `data/runtime/memory.db`、`memory.db-wal`、`memory.db-shm`、旧版 `memories.json` | 经记忆存储模块和 SQLite 事务更新；数据库运行时文件必须作为整体管理，不能单独删 WAL/SHM |
| 参数与模型 | `data/runtime/settings.json`、`models.json` | 通过控制台或机器人设置入口更新；不要手工改写运行中进程正在读写的文件 |
| 业务状态 | `data/runtime/clock.json`、`*_state.json`、`conv_state.json`、`memory_extract_state.json` | 由所属模块写入；清理前查 `docs/开发日志.md` 的数据文件说明，确认重启、重发、重抽取的影响 |
| 人格状态 | `data/runtime/persona/<包>/` | 表层、候选、信号、评估和审计，**按包分开**；遵守上方权属表，变更可追踪、可恢复 |
| 媒体资源 | `data/runtime/stickers/` | 图片文件由采集逻辑写入，`index.json` 由表情包模块维护；避免脱离索引直接改名或删除 |
| 运行日志 | `data/runtime/logs/bot.log` | 追加诊断输出，不承载业务状态；按日志规范脱敏和轮转 |
| 备份 | `data/runtime/_backup_日期/` | 只读恢复来源；备份创建时间和来源写在恢复记录里，不覆盖唯一的当前数据 |

新增持久化文件前，先确定它属于以上哪一类、权威路径是什么、谁是唯一写入者、是否可重建、怎样备份/恢复、删除会造成什么影响，再更新对应目录地图。多进程共享时先设计锁、原子替换或数据库事务，禁止靠“通常不会同时写”作为并发策略。

### 源码改动边界

- 一个模块只负责一个相对稳定的业务职责；跨模块共享的路径与配置通过现有配置入口，不在模块内部重复拼项目根目录。
- 业务代码不得向项目源码根或当前工作目录散落运行输出；媒体、缓存、聊天记录和状态都进入明确的数据根目录。
- 新增写入必须指定编码、失败处理、覆盖/追加语义及并发策略；整体状态文件使用同目录临时文件和原子替换，追加日志或 JSONL 保证每条记录完整。
- 改数据格式时为旧版本定义读取兼容或迁移路径，迁移必须可重复执行且不能静默丢字段；SQLite schema 变更通过存储层完成。
- 更新模块职责、数据路径或人格规则后，同步修改插件地图、根 README 的目录概览与文档入口，以及 `docs/开发日志.md` 的目录与数据文件说明和本规范中的权属表。
