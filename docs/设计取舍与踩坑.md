# 设计取舍与踩坑记录

这份文档记的是**这套框架为什么长成这样**。每一条都是实际调试出来的，
不是设计时的空想 —— 其中不少是"先写错了、现象很隐蔽、最后定位到根因"的产物。

> **第一次读这个仓库**：建议先翻到文档末尾的「14. 模块地图」，看清 34 个模块怎么切、
> 依赖是什么形状（尤其那 3 组**双向依赖**），再回来读下面按主题排的取舍 ——
> 知道东西在哪，这些坑才对得上号。

---

## 0. 总的取舍：宁可少花钱，也不要把上下文堆给模型

普通聊天机器人靠"携带对话历史"工作，上下文只会越来越长。这套架构反着来：

```
未读 → 原样塞进 prompt            （贵，但准确）
已读 → 按 READ_BUDGET 压缩         （便宜，越早越先丢）
```

省 token 的关键不在压缩算法，而在**什么时候把"未读"变成"已读"**。
答案是**会话切分**：两条消息间隔超过 `AI_CHAT_SESSION_GAP`（默认 300 秒）就算新的一轮，
开新一轮时把上一轮遗留的未读**全部归档为已读**。

于是「没人 @ 机器人的闲聊」会尽快降级成可压缩的背景，而不是堆在"未读"里
等着被一次性灌进去。人少、闲聊稀疏的群把间隔调到 180~300 就行。

**代价也是明确的**：被压缩掉的更早记录模型就看不见了。这一条后来用
「会话摘要」（§3）和「翻旧账」（§6）两个机制补上，而不是靠调大预算。

## 1. 人格三层：用文件划分把权限钉死

### 之前的写法，以及它为什么不可靠

最早是「一个 `persona.txt`（10 KB，人和模型都能改）+ 一堆运行时槽位
（`/人设` `/风格` 改的值存在 `data/persona_directives.json`）」。

问题在于：**"哪些能自动变"没有结构性保证，只有约定**。

- 底色和"可以慢慢学的东西"挤在同一个文件里，文件第 3 行还写着"下面写的是底色，改起来很慢"；
- 运行时槽位是第三处，谁都能写；
- 结果是想给自动迭代加权限时，只能靠"改代码时记得别碰另外两处"。

### 现在的写法

按**寿命与权限**拆成三个文件：

| 层 | 文件 | 谁能写 | 进 prompt 的位置 |
|---|---|---|---|
| 底层人设（它是谁） | `persona/packs/<包>/base.txt` | 只有用户（直接编辑文件） | 第 1 位（最硬） |
| 禁止事项（铁律） | `persona/packs/<包>/forbidden.txt` | 只有用户（直接编辑文件） | 第 2 位 |
| 表层人设（怎么说话） | `data/runtime/persona/<包>/surface.txt` | 只有自动迭代（须过冲突闸门） | 第 3 位 |

> **包化（2026-10）**：原来这三个文件平铺在仓库根目录（`persona_base.txt` /
> `persona_forbidden.txt` / `persona_surface.txt`），现在收进 `persona/packs/<包>/`，
> 一个目录 = 一套人格，换角色 = 换目录且**不用重启**。包内那份 `surface.txt`
> 只作**首次播种**的模板，实际生效、被自动迭代写入的是
> `data/runtime/persona/<包>/surface.txt`（在挂载卷里）。权限划分与下面这条保证不变。

现在的保证是**代码层面拿不到另外两个文件的写路径** ——
`persona_iter.py` 里根本没有 `persona_file_path()` / `forbidden_file_path()` 的调用。
测试里直接断言 `persona` 模块不存在 `set_directive` / `add_style_note` 这类函数。

**顺序有实际意义**：越靠前的内容对模型越像"前提"，越靠后越像"补充"。
所以底色 → 铁律 → 表层，表层即使写得天花乱坠也压不过上面两层。

### 禁止事项为什么单独成层

不是为了好看，是因为它要被**逐条解析出来做冲突判定**：
自动迭代生成一条候选改动时，要在关键词层面比对它是否碰了铁律
（`persona.forbidden_items()`），碰了就直接丢弃、不写入。
如果禁止事项还混在底层人设里，就没法单独解析。

### 冲突闸门的判定分级

`persona.validate_surface()` 返回 `(是否通过, 状态码, 原因)`，状态码是封闭集合：

| 状态码 | 含义 |
|---|---|
| `ok` | 正常通过 |
| `ok_negated` | **逆向表述放行** ——"不要用客服腔说话"是在重申铁律，不是违反它 |
| `too_short` | 太短，信息量不足以成为一条规则 |
| `forbidden_kw` | 命中禁止事项关键词 |
| `base_pronoun` | 试图改动身份代词（"你其实是一个男生"） |

`ok_negated` 这条是踩出来的：一开始只做关键词命中，
结果"不要用客服腔"这种**站在铁律这一边**的表述被自己拦掉了。

### 一个非结构性的观察：否定句密度太高

实测统计一份人设正文（3922 字符 / 166 行）：`不要` 28 次、`别` 25 次、
`不许` 3 次、`禁止` 3 次 —— 合计约 59 处**否定式约束**，而 `必须` 0 次、`优先` 1 次。

这类写法的已知代价是：模型记得住"不许做什么"，却不一定知道"该做什么"，
表现就是**过度克制、短到没话说**。

改法（低成本、纯文本）：把核心几条改写成**正向行为** ——
「不写括号动作」→「直接写对白」；「不谈论你自己」→「只聊对方和你眼前的事」。
一次只改 3~5 条，改完对比一周的回复长度分布，**别整篇重写**。

## 2. 分清"自己说的话"和"别人说的话"

### 现象

模型会对着自己上一轮的回复接话，或者把别人夸它的话当成自己说过的。
这是**真实出现过的毛病**，而且有两个独立成因：

| 成因 | 表现 |
|---|---|
| **格式没有说明** | prompt 里只有 `[14:02 机器人名] xxx`。模型不知道带标记的是谁 |
| **身份靠名字认** | 机器人自己的发言在记录里的名字就是它的显示名。**换人设改名之后**，历史记录里的名字对不上了，老发言就被当成"另一个人" |

### 处理

**① 三种身份在 prompt 里长得不一样**

```
[14:02 某某（主人）] 她是不是有点敷衍
[14:02 机器人名（你）] 才没有，我认真着呢      ← 自己说的，明确标出来
[14:03 张三] 哈哈她嘴硬                      ← 别人，原样
```

**② 「自己」的判定优先用 QQ 号，不靠名字**

落盘时把当时的 `bot_uid`（机器人自己的 QQ 号）一并存进每条消息。
改名、换人设、重启都不影响识别；老记录没有这个字段时退回 `is_bot` 标记，
最后才退回按显示名比。标记文案在 `config.BOT_SELF_LABEL`（默认 `（你）`），
**不建议改成空串**。

**③ 格式说明搬进代码，不再写进人设文件**

以前这段说明是人设正文的一段。问题在于：正文是**人设**，换角色时会整份重写，
格式说明就跟着丢了 —— 而格式说明是**机制**，不该跟角色走。
现在由 `context.record_legend()` 生成，换谁的人设都一定在。

**④ 两道防"回灌自己"的兜底**

* `recorder` 认出「这条是自己发的」→ 记成已读、**不触发任何回复判断**。
  否则它说的话里带了唤醒词，就会**被自己叫出来**对自己接话；
* `render_unread()` 跳过机器人自己写的行 ——「刚才的新发言」的含义是**别人说了什么**。

> 这四条都有离线验证用例覆盖，包括"改名后重启还能认出是自己"
> 和"人为制造一条未读的自己发言，确认它被跳过"。

## 3. 数据不再丢：四条边界

改造前有四处会**永久丢数据**，而且都不报错 —— 表现只是"它忘了""接不上话"。
四条修复都是**纯新增**，没有改动任何现有的读取路径。

### ① 超出上限是「归档」不是「删除」

原来的写法是 `del self.messages[:n]`。默认 `AI_CHAT_MAX_MESSAGES=0`（不限）
所以没触发过，但**一旦有人配了就永久丢**。

现在改成挪进 `data/chatlog_<会话>.archive.jsonl`（一行一条、只追加），
启动时扫一遍这个文件把 id 记进 `archived_ids`，
避免"归档 → 又读回来 → 再归档"来回搬。

### ② 损坏的文件改名留证，而不是被空库覆盖

原来解析失败时只 `logger.warning` 然后**从空记录继续** ——
那句"旧文件留在原地备查"是假的：下一次 `save()` 就把一个
**可能可以手工修回来**的文件原地覆盖了。

现在两条路径（chatlog / memory）同一个策略：

1. 原文件改名成 `<名字>.corrupt-<时间戳>`，**留证**；
2. 本次运行进入**只读模式**（`save()` 直接返回并记一条 error），绝不覆盖。

记忆库进只读时启动日志会显式打一条 `⚠ 记忆库处于只读模式` ——
因为它的现象是"它答应记住却总是忘"，不点名的话极难查。

### ③ 会话切分被当成免费的时间轴锚点

`append()` 检测到间隔超过 `session_gap` 时会话号 +1。这一刻：

* 上一轮的内容**已经定型**，不会再有新消息进来；
* `messages[].session` 已经能精确定位"哪些消息属于那一轮"。

所以它是**免费**的锚点，两个下游直接受益：

| 下游 | 用它做什么 |
|---|---|
| `summaries.py` | 给"刚刚结束的那一轮"生成一两句摘要 |
| `memory.drain_extraction()` | 只处理"已经定型的轮次"，避免和回复路径重复抽同一批 |

内部标记 `_rolled` 用下划线开头，`save()` 落盘时**被过滤掉**，
磁盘格式一个字段都没变。

### ④ 会话摘要：被丢弃的背景降级成摘要，而不是消失

`read_budget` 默认 2000 字符，**从最新往回累加，装不下的更早记录直接丢弃**。
按中文群常见的 10~40 字一条算，2000 字符大约只装得下 **50~100 条** ——
而实测单个群一天就能到几百条。所以"模型只看得见最近几十条"是常态。

现在每个**会话切分点**异步生成一句客观摘要，注入时挂在原文背景之后：

```
【更早几轮的摘要】（原文已经不在上面的记录里了，这些是当时发生的事的归纳）
- 14:02~14:41：聊到某个项目，主人说下周要交图；机器人答应帮他核对数值。
- 20:11~20:35：有人问某个名词是什么，机器人联网查完给了释义。
```

| 设计 | 为什么 |
|---|---|
| 触发点是**会话切分**，不是定时任务 | 切分天然是"一轮结束"的边界；不必另建索引，也不会在活跃群里反复烧 token |
| 摘要**不写进记忆库** | 它的寿命与失效条件和事实条目不同，混进去会让淘汰逻辑同时管两种语义 |
| **不删原文** | 摘要只是"回顾入口"，原始记录永远留在 `chatlog_*.json` 里 |
| 失败不重试、不抛 | 摘要丢了只是那一轮没有回顾入口，属于可接受降级 |
| 提示词要求**只写记录里确实出现的事** | 明确禁止写情绪氛围、关系变化，也禁止把一件事安到错误的人头上 |

## 4. 长期记忆：本地打分，不引向量库

### 打分公式

```
score = 0.45 × 相关度 + 0.25 × 重要度 + 0.15 × 时效 + 0.15 × 被用次数
```

相关度是 **n-gram 重叠**，时效用半衰期（默认 30 天）。
`_RELEVANCE_FLOOR` 保底塞词面最相关的几条，`protected` 的条目额外加权。

**为什么不用向量库**：这一层真的**不花 token**，也没有额外服务要养。
代价是**跨语言同义匹配不到**（"面试" ↔ "找工作"），这是刻意的取舍。

### 改口要覆盖，不是追加

不能用 `value not in merged` 这种**精确字符串**比对 ——
模型每次换个说法（"作息偏晚" / "经常熬夜" / "常在深夜到凌晨活跃"）就被当成新条目。
实测某个人的 habit 里同一件事**占了 4 条**，把配额吃掉 1/3，
后面更好的信息反而被挤掉。

现在的做法：2-gram 相似度命中就**覆盖**并留 `prev_text`，重复时保留信息量更大的那条。
抽取路径还能由模型带 `prev_text` 走 `_find_by_text()` 显式更正。

### 「被反复用到的更容易被想起」曾经是假的

`used` / `last_used` / `hits` 三个字段一度只是在写、从来没被读。见 §5 的教训。

### 隐私边界：打分**前**过滤，不是降权

早期实现里 `add_fact` 默认 `scope="global"`，`retrieve()` 只对
`scope=="event"` 且会话不匹配的**减 0.25 分** —— 也就是**降权而非排除**。
现实后果：私聊里说的事，机器人在群里可能顺嘴讲出来；A 群听说的八卦，B 群也可能被带出来。

现在给事实加 `vis` 字段（可见会话列表，`["*"]` / `["g<群号>"]` / `["u<QQ>"]`），
`retrieve()` 里**在打分之前**按当前会话 + 发言人过滤。

**为什么必须"排序前"而不是"排序后"**：排序后再过滤，会让"被过滤掉的条目
挤掉了本该入选的条目"—— 名额被不合法内容占了，召回数量凭空变少。

### 身份归一：一个 QQ 号只有一份画像

`facts` 有 `uid` 字段，但早期自动抽取路径**从不写 uid**（只传 `name=subject`）。
于是同一个 QQ 号在不同群的昵称会写成不同 `subject`，一个人分裂成好几个人：

- 连锁反应一：`retrieve()` 的按名字加权只命中一半；
- 连锁反应二：`render_profile()` 按名字匹配，"提到谁就带谁的画像"只命中一半。

现在抽取时就把 `subject` 落到 `uid:<QQ号>`（`entity.uid_key`），
画像键也跟着归一。

### 键长度限制吃过亏

画像键原来被 `_clean(key, _MAX_KEY=24)` 砍到 24 字，
导致群里长昵称被截断 —— **同一个人因为每次截法不同，会分裂成好几个画像键**，
去重也就失效了。现在键用 40 字上限，与 `_MAX_NAME` 一致。

## 5. 「被反复用到的更容易被想起」曾经是假的 —— 一个真 bug

一组字段（`used` / `last_used` / `hits` / `last_hit`）在落盘结构里存在，
代码里也一直在写，但**没有任何读取路径**。也就是说：

- 「用得多的记忆权重更高」在文档里写着，在代码里从来没生效过；
- 更糟的是它**不报错**，看上去一切正常，只是记忆的召回质量一直低于预期。

**这类 bug 的共性**：现象是"效果比预期差"，而不是"报错"。
所以只靠跑测试发现不了 —— 测试断言的是"字段被写进去了"，而这个断言一直是真的。

修复方式是补上读取路径，并把「被想起次数」攒着批量落盘
（`AI_CHAT_MEMORY_USED_FLUSH_SECONDS`，默认 60 秒），
避免每轮回复都触发一次磁盘写。

## 6. 翻旧账：全量记录得能查

`read_budget` 背后的取舍是"只留最近的"。但盘上其实留着**全量** `messages[]`，
只是**没有任何代码路径能把它捞回 prompt**。于是"你上周是不是说过……"
这类问题结构上答不了。

现在给每条消息建**词面倒排索引**（`msgindex.py`，存 SQLite）：

| 设计 | 为什么 |
|---|---|
| 索引**归档文件一起进** | `chatlog_*.archive.jsonl` 里是超上限被挪走的老消息，不索引等于刚做的归档白做 |
| `messageid` 幂等（按 `conv + msg_id` 覆盖） | 增量补索引要能重复跑 |
| 启动时**必须**补一段历史索引 | 否则重启后旧记录永不入索引 |
| 回忆类问题用「事件 / 关系 / 心情」三个角度各召回一次再合并 | 单一查询词对回忆类问题召回太窄 |

> 老消息的文本形态可能是**旧版渲染格式**。索引是按词面切的，
> 所以格式变更不会让历史索引失效 —— 这也是选词面索引而不是向量索引的一个附带好处。

## 7. 联网搜索：什么时候该搜，比搜得快更重要

### 症状

**一联网搜索就把整句话全贴上去，搜回来的东西毫不相关。**
根因是三层叠加：

1. 搜索上下文传的是整段 `user_text`，而它末段是**会话统计行**，
   被 `[-40:]` 抓去当关键词；
2. `query_from` 只削词不抽词，"那为什么不回应你的主人"削完纹丝不动；
3. 触发词含「为什么 / 怎么 / 吗 / ？」—— 几乎每句话都能命中。

### 修法

* 查询**不再拼上下文**，只从"本次要回应的发言"里取；
* **抽词优先于削词**；
* 拧不出关键词就**不搜**（宁可这次不搜，也不要搜一个必然跑偏的词）；
* 加 `_looks_like_query` 形状护栏：位置标记（`[22:24 张三]`）、标点、
  会话统计行混进查询 → 判定为"上下文没剥干净"，放弃这次搜索。

**一个通用教训**：给模型的工具的"要不要用"判断，比"用得多好"更容易出错。
所以判定逻辑要**保守**（默认不搜），并且判定失败要静默 —— 不要告诉模型"我搜失败了"，
它会开始解释一个用户根本没问的事。

### 防注入渲染

搜回来的网页原文是**不可信内容**，里面可能写着"忽略之前的指令"。
所以：

* 正文只截取前 N 字（`AI_CHAT_SEARCH_READ_CHARS`，默认 800）—— 这也是 prompt 成本的主开关；
* 渲染成明确的数据块，与指令区隔开；
* 查过之后在回答前加一句说明（**由代码加，不靠提示词**），
  这样即使内容被污染，群里也能看出"这是从网上来的"。

### 浏览器渲染是最后手段，不是默认路径

百度百科、知乎对机房 IP 段直接 403（换 UA / Referer 都没用），
但它们拦的是"HTTP 客户端特征" —— 真浏览器渲染出来的 DOM 是完整可读的。

代价：单页 3~8 秒、峰值内存 200~300 MB。所以**只在 HTTP 失败后才走**。

> 实测 DOM 又准又快（11706 字 / 8 秒），OCR 又慢又少（836 字 / 37 秒），
> 所以正常情况下根本不会触发 OCR。OCR 只服务于"DOM 里真的没有文字"的情况。

## 8. 读网页正文：防 SSRF 是硬要求，不是加固项

URL 是**模型给的**。所以只允许公网 http/https：

1. DNS 解析出的**每个** IP 都要是公网地址 ——
   挡掉 `127.0.0.1`、`10.x`、`192.168.x`、`169.254.169.254`（云元数据）；
2. **每一次重定向都重新查** —— 否则"公网域名 → 302 → 内网"就绕过去了；
3. 限制体积与超时，防止被一个超大响应拖死。

**为什么这么严**：真让它去读 `http://169.254.169.254/` 或同网络里的
NapCat 管理页，后果不是"读不到网页"这么轻。

## 9. 其他踩过的坑

### NoneBot2 的 Config 是 `extra="allow"`

字段**没配时取到的是 `None` 而不是"没有这个属性"** —— 所以
`getattr(cfg, name, "默认值")` 的默认值**永远不会生效**。

历史事故：写成 `getattr(..., "persona.txt") or ""` 之后人设文件被静默跳过，
机器人退化成一句内置通用提示词，而日志里一个字都没有。

现在三个文件名的取值一律 `getattr(cfg, name, None)` 再显式分流 `None` / `""`。

### NoneBot2 的自定义字段只从 `.env` **文件**读

已声明的字段（`driver` / `port` …）能从环境变量读，
但插件用的那些**自定义字段**（`deepseek_api_key`、`ai_chat_*`）只会从 `.env` 文件里读。

而 `Dockerfile` 故意不 `COPY .env`（防密钥进镜像层），于是容器里只有环境变量、
没有文件 —— 结果所有自定义配置**静默退回代码默认值**。

实测症状：`docker echo ${#DEEPSEEK_API_KEY}` 返回 35 个字符，
机器人却照旧回「我还没拿到 API Key」。

解法见 `deploy/docker-compose.yml`：把 `.env` 只读挂载进容器 `/app/.env`。
**这个文件必须先存在**，否则 Docker 会把它当成目录创建出来。

### Windows 控制台的编码

Windows 默认 GBK 代码页，日志里只要出现 emoji，loguru 就会抛
`UnicodeEncodeError`，**那一条日志直接丢失**（不中断程序，所以很难发现）。

启动脚本里固定 `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1`。

另外：PowerShell 5.1 的 `Tee-Object` 没有 `-Encoding` 参数，它按 UTF-16 落盘，
会和 UTF-8 表头混进同一个文件。所以启动脚本用 `StreamWriter` 自己写。

### 时间必须由代码提供，不能让模型算

模型不知道"现在几点"。不给它，「现在几点了」只能瞎猜，
「早安」和「晚安」也分不出该说哪个。

但分工要清楚：

| 谁做 | 做什么 | 为什么 |
|---|---|---|
| **代码** | 当前时刻、"过了多久"、跨天判断 | 这些是**精确算术**。让模型算「三天前是几号」既慢又会错，而本地算一次 0 token |
| **模型** | 读懂"刚吃过饭""昨天下午"这类模糊表达 | 这是**语言理解**，代码做不了 |

**NTP 校准只取偏移量，不改系统时钟** —— 改系统时钟要管理员权限，
还会影响同机其它程序。之后的每次时间读取都加上这个偏移。

时区是个隐蔽的坑：容器跑在 UTC 而不是 `Asia/Shanghai` 时，
时间感知会答错 8 小时，**定时问候也会在错误的钟点触发**。
所以注入 prompt 的时间戳带 `%Z%z`，一眼能看出时区对不对。

### 熔断要用本地时钟

限流 / 冷却用的是 `clock.now()`（已校准）。如果 NTP 把时钟往回拨，
用原始 `time.time()` 算出来的"冷却还剩多久"会算错。

### 图片去重：认内容，不认字节

同一张图被重新压缩 / 缩放 / 转格式后**字节全变**。
靠 pHash（64 位感知哈希）+ 汉明距离判断是不是同一张。

实测同一张图做各种变换都是 0 位差异；阈值调到 12 以上会开始
误杀"很像但确实是两张"的表情。没装 Pillow + numpy 时自动退回精确去重。

**QQ 的"发送文件"选一张图**，上报的是 `file` 段、`sub_type` 全是 0，
看不出是不是表情包。这类通常是照片 / 素材原图，
所以打分时直接扣掉一档（`AI_CHAT_STICKER_FILE_PENALTY`）。

### 分条发送的阈值别调大

一次回答里有好几个短句时逐句分次发，像真人打字。但合并阈值
（`AI_CHAT_SENTENCE_MERGE_UNDER`）**别调大** ——
调到 6 会把「先看耐压。」（5 字）这类正常短句也并掉，三句就只剩两条。

---

### 清空记忆只清在内存里（穿透容器没覆盖 `clear()`）

`_WriteThroughList` / `_WriteThroughDict` 用「覆盖 `append` / `remove` / `pop` /
`__delitem__`」的办法，让算法层照旧直接操作列表与字典、落盘自动发生 ——
但 `clear()` **没有被覆盖**。

于是 `memory.clear()` 里的 `_db.facts.clear()` / `_db.profile.clear()` 只清了内存：

* **JSON 后端看不出来**：它的 `save()` 会把整库重写一遍；
* **SQLite 后端就出事了**：它的 `save()` 只补一个 `meta.next_id`、**不整库重写** ——
  回执说"清掉了 N 项"、控制台里也确实空了，**重启之后旧条目原样回来**。

这条路径就是 `/记忆 清`（含 `/记忆 清 画像`）走的。**"看起来成功"的失败最贵**：
没人会专门去重启验证一次。

现在改成逐条 `remove` / `pop`（这两个本来就会穿透到 SQL 删除）。
回归测试的关键是**重新打开 `memory.db` 再断言** —— 只看内存里的计数是验不出这个 bug 的。

## 10. 若干数值为什么是那个值

| 参数 | 值 | 依据 |
|---|---|---|
| `AI_CHAT_SESSION_GAP` | 300 秒 | 人少、闲聊稀疏的群可以降到 180~300 省更多 |
| `AI_CHAT_READ_BUDGET` | 2000 字符 | 按 10~40 字一条算，约装 50~100 条；人少的群可降到 800 |
| 记忆半衰期 | 30 天 | "一个月前的记忆权重减半"这个直觉 |
| `_RELEVANCE_FLOOR` | 0.18 | 低于它就基本是噪声；调到 0.3 以上它就不太主动提记忆 |
| pHash 汉明距离 | 8 | 同图各种变换实测 0 位差异；12 以上开始误杀 |
| 群事件保留 | 180 天 + 2000 条 | 时间窗 + 条数**双重**上限，防只增不减 |
| 记忆抽取 | 每天 200 **条消息** | 口径是条数不是次数 —— 写成次数时一次抽 40 条会把额度一次吃光 |
| 自动迭代间隔 | 21600 秒（6 小时）+ 每次最多 2 条 | 改太多就分不清是哪条起的作用 |
| 反思最少对话行数 | 20 | 太少会让它瞎猜 |

## 11. 已知的、还没解决的取舍

写在这里是为了避免"以后以为是 bug"：

1. **跨语言同义匹配不到**（"面试" ↔ "找工作"）。这是不引 embedding 的代价。
2. **`strip_self_meta` 是纯字符串规则**，误删 / 漏删只能靠加正则补。
   动它收益低于风险，所以维持现状。
3. **检索仍没有可信度分层。** 已做的一半见 §12.1（`manual` 与 `extract` 分开了），
   但"一条自动抽取的猜测该有多可信"仍然只靠 `importance` 一个模型自填的数。
   真正的分层（猜测 → 强化 → 事实）没做。
4. **没有"我改口了"和"从没发生过"的区分** —— 两者在库里都是 delete。
5. **Web 控制台没有认证**，安全性完全依赖"端口只绑回环 + SSH 隧道"。
6. **本框架不管 NapCat 的启动**：它的启动方式随平台与安装方式差异很大，
   强行统一只会引入一堆平台判断。
7. **受保护 / 手动的记忆条目会削弱容量上限**（§12.1）。已在淘汰不动时记 warning、
   并把 `evictable` 报给控制台，但没有自动策略 —— 该由人决定留哪些。
8. **摘要库仍是"每会话一整个 JSON 文件"**。它现在是原子写 + 损坏留证，
   但每个会话的还是整份重写；会话一多、摘要一长，写放大会变明显。
   真要治得按会话分文件（见 §12.2 的取舍说明）。

## 12. 第二批：四处"静默失效"的修补（2026-09-25）

这一批的共同点是：**问题都不报错**。它们的现象是"效果比预期差""看着一切正常"，
所以只靠"跑一遍测试没挂"发现不了 —— 下面每条都注明了它是怎么暴露的。

### 14.1 「人说的」与「模型猜的」必须结构性分开

记忆库里的每条事实都只有一个 `importance` 浮点来区分轻重，而**那个数是模型自己填的**。
于是一条自动抽取出来的猜测（"他可能喜欢吃辣"）和用户明说的
"下周三要面试"，在库里长得一样、打分也一样。

但 `source` 字段本来就在（`/记忆 存` 写 `manual`、自动抽取写 `extract`），
**只是从来没参与打分**。现在给它三处结构性差异：

| 位置 | 改法 |
|---|---|
| 打分（`score_fact`） | 新增 `_W_MANUAL` 独立权重；各权重按比例微调以保持总和为 1 |
| 淘汰（`compact`） | `manual` 与 `protected` **一律不淘汰**；两者都判，因为老数据可能只带其一 |
| 入库（`add_fact`） | `protected` 默认值改成"按来源决定"：`manual` 默认保护，`extract` 不保护 |

还有一个**必须留的反向口子**：显式传 `protected=False` 要能被尊重，
否则批量导入时会静默把所有条目都设成不可淘汰。

**代价要写清楚**：受保护的条目一多，`memory_max_items` 就名存实亡、库会一直长。
所以 `compact()` 在"该淘汰却淘汰不动"时**记一条 warning 点名这件事**，
`stats()` 也报出 `manual_protected` 与 `evictable` 两个数 —— 这类"看起来没爆但一直在涨"
的状态最难查，必须在人能看见的地方说出来。

### 14.2 摘要库坏了：不能就地覆盖

`chatlog` 和 `memory` 早就有"损坏就改名留证"的策略，**只有会话摘要库漏了**：
它读不出来就记一条 warning、按空库继续，而下一次 `_save()` 会把那个损坏文件
**原地覆盖** —— 「读不出来就当没有」和「把证据抹掉」是两件事。

现在它跟另外两个用同一个姿势：改名成 `<名字>.corrupt-<时间戳>`，再重新开始。
但它**不必进入长期只读**（摘要只是"回顾入口"，原文还在 chatlog 里），
所以留证成功就继续记；只有"连改名都失败"（权限/被占用）时才放弃本次写盘。

> **写这段时踩到的坑**：一开始把"只读标志"在 `try` **之前**就设上了，
> 于是"改名成功"这条正常路径也被自己的标志拦住、再也写不出新库。
> 标志只在 `except OSError` 里设才对。测试里钉住了这一条。

顺带把 `_save()` 改成 `flush + fsync + replace`：摘要是**整份重写**的，
少了 fsync 的话掉电/强杀可能留下一个"文件名对、内容是半截"的 JSON ——
而那正是这一步要防的东西。

### 14.3 自动迭代不再直接生效

冲突闸门只拦"碰铁律"，**拦不住风格跑偏**：学成话痨、学成另一个语气。
这类改动照样过闸门、下一轮就生效，而人在群里只会觉得"它今天怎么怪怪的"，
根本不知道人格文件被动过。

现在默认走**候选池**：

```
自动迭代产出 → 过闸门 → 合规的进 data/persona_candidates.json + 通知
                        → 人 /人设 采纳 <序号> 才写进表层
             → 碰铁律的 → 当场丢弃（连池子都不进）
```

闸门在"进池"这一步就跑，所以池子里不会有违反铁律的东西 ——
人只需判断"像不像它"，不必重新审一遍合规性。
`/人设 否决 <序号>` 走另一条路，**否决本身也记进日志**（那是判断闸门松紧的依据）。

`AI_CHAT_PERSONA_ITER_AUTO_APPLY=True` 可以退回改造前的直接生效行为。
两条路径**都要有用例守着**：老路径由 §33 覆盖（显式打开那个开关），
新默认值由 §34 覆盖 —— 否则"验的是什么"会随默认值悄悄漂移。

### 14.4 历史轮次的摘要缺口，不会自愈

摘要的触发点是**会话切分**，也就是"功能上线之后新结束的那一轮"。
上线之前盘上已有的轮次永远不会被总结，而 `render_background()` 又确实会把它们丢掉 ——
于是那段时间只剩一句「更早的 N 条原文没有放进本节」，后面是**没有摘要的空白**。

这个断层不会自愈：切分只处理"刚结束的那一轮"，没有任何路径往回看。
所以它是一个一次性回填脚本（`_工具链/维护/_回填摘要.py`），和"补长期记忆"的
`_补提取.py` 是同一类东西。

**缺口判定放在插件里**（`summaries.missing_sessions()`）而不是脚本里：
同一份逻辑放两处迟早漂移，而漂移的表现是"漏补了几轮" —— 又是一类不报错的错。
脚本只负责"怎么补"，而且先从**最新**往回补（最近的轮次对回顾最有用，
万一半路到了调用上限，缺的是最久远的那几轮）。

> **写脚本时踩到的坑**：`--limit` 原本用全局计数判断，于是第一个会话补满之后
> **后面所有会话一条都不补、而且不报错**。每会话的上限就必须每会话重置 ——
> 静默少干活是最难发现的那种错。

## 13. 测试基建本身修掉的两个缺陷

这一批里最值得记的可能不是功能改动，而是**测试套件自己的两个问题**。
它们的共同点是：**让一批用例静默地不跑**，而剩下那半绿的看起来很健康。

### 15.1 临时目录建了却不可用

套件开头写着"全程写临时目录，绝不碰真实的 data/"，但：

1. `tempfile.mkdtemp()` 落在 `%TEMP%` 下，而本机沙箱对那个位置**没有写权限**；
2. 就算挪进工作区，`tempfile.mkdtemp()` 建出来的目录**本身仍然写不进去**
   （实测 `PermissionError: [Errno 13]`）—— 而用 `Path.mkdir()` 建的同级目录可写。

失败被各处 `except OSError` 吞掉、只留一条 warning，于是"策略落盘"那条断言永远失败，
**套件在它之后就中断了** —— 后面三千多行用例从来没被执行过。
改用 `Path.mkdir()` 在工作区内自建目录之后，套件第一次跑到了末尾
（项数从 803 涨到 862，多的那些本来就是存在的用例）。

### 15.2 一条断言失败不该让整批不跑

"策略落盘"那条断言直接 `json.loads(path.read_text())`，文件不存在就抛
`FileNotFoundError`，把整个进程带走。现在改成 `try/except` + `check(False)`：
**失败要记下来并继续**，而不是中断。

> 这两条合起来说明一件事：**"没报错"不等于"跑了"**。
> 一个能静默跳过用例的测试套件，比一个会挂的测试套件更危险。

## 14. 模块地图：34 个模块怎么切、"无环"是靠什么撑的

`plugins/ai_chat/` 有 **34 个模块、约 19,700 行**。这个切法不是"一个功能一个文件"，而是
**按关注点**切的，粒度也不算碎：行数中位数 471，只有 3 个模块不到 200 行，另有 12 个在 600 行以上
（最大的 `memory.py` 2,054 行 —— 它是内聚的，拆开只会引入更多跨模块状态）。

模块名基本就是职责名，照着找东西通常能找对：`context`（拼 prompt）、`chatlog`（落盘 + 已读/未读）、
`memory` + `memstore`（记忆的算法层与持久化层）、`persona` + `persona_iter`（三层人设与自我迭代）、
`settings` + `config`（运行时可改 vs 静态配置）、`untrusted`（外部文本进 prompt 的**唯一**通道）……

### 依赖的真实形状

| 指标 | 实测 |
|---|---|
| 模块级（顶层）导入边 | 132 |
| 模块级依赖图有环吗 | **没有，是 DAG** |
| 函数内"延迟导入"边 | 24 |
| 真正**双向**依赖的模块对 | **3 组** |

被依赖最多的三个：`settings`（24 个模块顶层导入，自己一个同包依赖都没有）、`config`（22 个）、
`clock`（12 个）。方向基本单向：底座 → 上层。

### 那 3 组双向依赖（新读者最容易踩的坑）

| 模块对 | 为什么互相需要 | 现状 |
|---|---|---|
| `clock` ↔ `config` | `clock` 要 `config` 的日志目录，`config` 又要 `clock` 的"现在几点" | 两侧都在函数内导入 |
| `fetch` ↔ `render` | 抓不到正文时 `fetch` 调 `render` 拿浏览器截图；`render` 又要复用 `fetch` 的下载 | 两侧都在函数内导入 |
| `instructions` ↔ `introspect` | `instructions` 要 `introspect` 的自我说明，`introspect` 要 `instructions` 的指令表 | 两侧都在函数内导入 |

**动这 6 个模块里任何一个之前，先看它的对手模块。** "模块级无环"是**结果**，
不是"这些概念彼此独立"的证据 —— 真实调用关系是网状的，只是把环推到了调用期。

### 一个反面提醒：注释里写的环，有一半已经不成立了

代码里有几条注释写着"避免 A ↔ B 顶部互导"，但按现在的代码，`chatlog` **完全没有**引用
`stickers` / `memory`（只在注释的叙述里提到它们）：

* `stickers.py` 那句"避免 `stickers` ↔ `chatlog` 顶部互导"——实际**只有单向**（`stickers` → `chatlog`）；
* `memory.py` 那句"`chatlog` 不能反过来 import `memory`"——那是一句**警告**（别把它变成双向），
  不是"现在有环"。

这是"注释写成现场记录"的代价：注释越像当时的实况，越容易在代码变化之后变成错的。
**读的时候以代码为准**；改的时候，凡注释里"当前如何如何"的句子都顺手核一遍。

### 注释的写法约定

这套代码的注释密度约 **25%**（注释 + docstring 4,000 行 vs 代码 12,600 行），而且**是刻意的**：
调试时最花时间的从来不是"这行在干什么"，而是"为什么必须是这个值、为什么不能那样写"。

但注释只写两类东西：

1. **现在的约束** —— "这里绝不能收「为什么」「怎么」「吗」「？」"；
2. **为什么是这个值** —— "实测最长才 63 字，所以上限 200 是浪费"。

**不写**：日期戳、批次编号、`活项目` / `分析记录/xxx.md` 这类内部指代 ——
读者在副本里无从对照这些名字，只会以为是断链。变更史与取证留在维护者的开发日志里，
不随副本分发：想知道"这条规则是哪一次改出来的"，在代码里找不到是**正常的**。
