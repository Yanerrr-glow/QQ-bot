## 3. 根因

### 3.1 画像与事实是并列输出，不是派生关系

当前 [`_extract()`](../../plugins/ai_chat/memory.py#L1608) 一次调用返回三个并列的桶：

```json
{"profile": [], "facts": [], "events": []}
```

[`_apply_extraction()`](../../plugins/ai_chat/memory.py#L1660) 分别写画像、事实和事件。也就是说：

- 画像不读 `facts` 表，事实库为空也能写画像；
- 代码里没有“事实升级为画像”的管道；
- 模型把某条信息写进 `facts` 后，当前没有自动回补画像的路径；后续聊天再次提到时仍可能重新抽取，不能理解为永远无法进入画像。

所以“只有能进 fact 才有资格进 profile”**不是代码规则，而是实际运行结果**：提示词只有一个总门槛“值得长期记住”，facts 的 schema 更宽、更像默认桶，模型拿不准时就往 facts 放；画像只是这次抽取顺带产出的副产品。

从数据语义看，正确关系应该反过来：

| 层 | 回答的问题 | 时间性 | 例子 |
|---|---|---|---|
| `events` | 这个会话里发生了什么 | 强，按会话隔离 | 今天面试了、群里决定周末聚会 |
| `facts` | 有什么可复用的陈述/决定/更正 | 中，可检索、可更正 | 他在做某个项目、他换工作了 |
| `profile` | 这个人稳定是什么样 | 弱，需要证据累积 | 喜欢某类音乐、不喜欢某种饮品、有早八 |
| persona signals | 他希望我怎么说 | 独立体系 | 别叫我某个称呼、少用表情 |

画像的资格应当是“**稳定 + 对未来对话有用 + 有证据**”，而不是“能写成一条 fact”。一条事实可以永远不进画像；一条画像也可以由多条单独看并不重要的聊天归纳出来。

### 3.2 提示词文字与输出 schema 不一致

[`_EXTRACT_PROMPT`](../../plugins/ai_chat/memory.py#L1590) 的正文要求提取“称呼、喜好、厌恶、习惯、职业、作息、正在长期做的事”，但给出的 JSON schema 只有：

```json
{"who": "显示名", "love": [], "dislike": [], "habit": []}
```

- “职业、作息、正在长期做的事”没有对应字段，只能落进 `habit` 或 facts；
- `note` 字段在表结构和 `set_profile()` 里存在，但**从未让模型输出**；
- [落库时的 `set_profile()` 调用](../../plugins/ai_chat/memory.py#L1727) 也没有传 `note`；
- 单次最多处理 4 个人（`[:4]`），事实/事件受 `memory_extract_max`（默认 3）限制；
- 提示词还写着“不确定是否重要时，宁可不提”，这会进一步压低画像召回。

模型输出不稳定已实测：同一段包含明确偏好的聊天，单独跑抽取时有一次返回了 `profile`，另一次返回全空；而线上同一批内容最终以 facts 落库。这说明不能只靠“让模型更努力一点”，需要结构性的第二道工序。

### 3.3 抽取时看不到现有画像

[`_extract()`](../../plugins/ai_chat/memory.py#L1608) 的 [`existing` 构造](../../plugins/ai_chat/memory.py#L1614) 只拼接最近 20 条 **facts**：

```python
existing = "\n".join(
    f"- {f.get('text','')}" for f in sorted(_db.facts, ...)[:20]
)
```

模型看不到“这个人现在已经有哪些画像”，于是：

- 无法做增量补充（“已知他喜欢 A，这次补一条 B”）；
- 无法判断是否重复；
- 容易把已经写进画像的信息再写一遍 facts，或者反过来。

### 3.4 画像写入没有可靠落盘（P0）

[`set_profile()`](../../plugins/ai_chat/memory.py#L703) 的写法：

```python
cur = _db.profile.setdefault(key, {...空默认值...})
...
cur["display"] = ...
cur["love"] = ...
cur["updated_at"] = _now()
```

问题在于：

- `setdefault` 会先以**空默认值**触发一次写入穿透，落下一行空画像；
- 后续 `cur[...] = ...` 是**原地修改嵌套 dict**，不会再触发 `__setitem__`；
- SQLite 后端的 [`save()`](../../plugins/ai_chat/memstore.py#L483) 只补 `next_id`，不会重写画像；
- 代码里没有任何地方在修改后显式调用 `upsert_profile()`。

[`consolidate_profile()`](../../plugins/ai_chat/memory.py#L919) 的 `setdefault` + 原地合并 + 删除旧键，存在同样问题。

临时库复现结果：

```text
内存里: {'uid:1': {'display': '测试人', 'love': ['喜欢甲'], ...}}
--- 模拟重启，重新从磁盘载入 ---
磁盘上: {'uid:1': {'display': '', 'love': [], ...}}
```

后果是：**画像内容只活在内存里，进程一重启就全丢，磁盘上只留下空壳行。** 这解释了为什么表里有 4 个键、内容却全是空；也意味着即使今天模型写出了画像，下次重启仍会丢。

> 注意：这条缺陷本身不能解释“当前内存里也为空”。当前为空还叠加了 3.2 —— 最近几次抽取根本没有产出 `profile`，而是写成了 facts。

### 3.5 渲染截断会吃掉覆盖率

[`render_profile()`](../../plugins/ai_chat/memory.py#L1403) 每个人只取：

- `love[:4]`
- `dislike[:4]`
- `habit[:3]`
- `note[:60]`
- 总预算 600 字；没有点名时回落到 300 字

也就是说，即使画像库变全，进入 prompt 的也只是前几条；按 key 排序靠后的人还可能被预算直接截掉。**“库里有”不等于“模型看得到”**。

### 3.6 缺少人工入口与覆盖指标

- Web 控制台的 `/api/memory` 只能新增事实，不能编辑画像；
- `/记忆 存` 只写事实，`/记忆 清 画像` 只能清空，不能补写；
- 没有“画像覆盖率 / 字段覆盖 / 新鲜度 / 渲染覆盖率”这类指标，无法判断改进是否有效。

## 4. 目标方案与实现约束

本节替代原方案中的“禁止双写”“画像只能从 facts 归纳”“所有自述必须两次才确认”等建议。下列接口、表、配置和文件名均为**拟新增设计**，不代表当前代码已有这些能力。

### 4.1 统一信息模型：证据层与画像结论分开

```text
聊天批次 → 提取带来源的陈述
                ├─ facts / events：可检索事实与会话事件
                └─ 画像证据 → 条目候选 → 确认 / 更新 / 撤回
历史 facts、旧 JSON → dry-run → 经审核的画像证据
已确认且有效的画像条目 → 兼容 profile 展示 → 按对话相关性进入 prompt
```

设计原则：

1. 画像可以直接引用原始消息，不要求消息先被选入 facts。不能沿用事实抽取的“最多 3 条”等配额限制画像证据。
2. 同一信息可以有事实记录和画像结论，关联来源即可；在最终 prompt 中去重，不能以“禁止双写”为由删除证据。
3. UID 是人物身份主键，显示名只作展示。旧名字无法唯一解析时进入待核对报告，不猜测归并。
4. 证据和画像必须继承来源的会话范围及可见性；私聊画像不能因同一个 UID 自动出现在群聊中。
5. 画像是条目集合；每个条目独立管理来源、状态、时间和有效期，不给整个人共用一个置信度。
6. “今天买了麻薯”是事件；“我喜欢麻薯”是偏好证据；“最近在找工作”是带有效期的临时状态。“有早八”应结合学期或时间范围，不能默认永久有效。

### 4.2 P0-A：可靠写入与原子归并

涉及 `plugins/ai_chat/memory.py` 的 `_Db / set_profile / consolidate_profile / _persist`，以及 `plugins/ai_chat/memstore.py` 的两个后端和写入穿透容器。

**接口契约（建议）：**

```python
# 以下签名为设计示意；具体类型与现有工程风格保持一致。
write_profile(key, snapshot) -> None
merge_profile_keys(source_key, target_key, merged_snapshot) -> None
commit_extraction(batch_id, changes) -> CommitReceipt
# 失败抛出 MemoryWriteError；只读状态同样不能作为成功返回。
```

实现步骤：

1. 在 `_Db` 建立统一方法，SQLite、JSON 均实现相同成功/失败契约。当前 JSON 后端没有 `upsert_profile()`，不能直接给业务代码补一次调用便认为兼容完成。
2. `set_profile()` 从旧值创建深拷贝，校验、去重后得到完整快照。禁止先 `setdefault` 写空行再原地改嵌套字典。
3. SQLite 先执行 SQL 并提交，成功后同步 `_raw_profile` 和公开 `profile` 缓存；缓存同步须绕开会再次写盘的容器钩子。失败回滚事务，缓存保留旧状态。
4. 归并使用同一个事务：读取源和目标、生成合并值、更新目标、删除源、提交。任一步失败都回滚，成功后才同步内存和记录成功日志。
5. JSON 使用独立的新 payload 写入同目录临时文件，再原子替换目标文件，完成后发布内存快照；替换失败保留旧文件和旧缓存。按运行环境落实 flush/fsync，断电级保证需单独测试，不能只凭 rename 宣称完成。
6. `SqliteStore.upsert_profile()` 当前捕获异常后只记日志，必须改为向上传递失败；只读保护也须返回明确错误。审计同一抽取批次里的事实、事件、实体、计数器写入，不能有任一失败被吞掉后仍推进水位线。
7. 调整 `_WriteThroughDict.__setitem__/pop` 的“先改内存再写盘”行为，或让画像写入统一绕过旧写穿透路径。避免业务接口修好后，清空和迁移仍走另一套不可靠逻辑。
8. 审计 `_Db.load()`：目前载入清洗会通过画像整体赋值触发写入；应将纯读取和有版本的规范化迁移分开，避免只读启动和加载意外修改数据库。

**更新语义必须显式：**

- 抽取使用 `merge`，只添加有效增量；重复输入不更新业务时间戳。
- 人工编辑使用 `replace`，允许列表 `[]` 和字符串 `""` 清空；未提供字段保持原值。
- 删除使用 `clear`，不通过传空值模拟。
- 当前 `set_profile()` 的注释称 `[]` 会清空，但实现合并旧列表；`note=""` 也不会清空。实施时审计所有调用方，保留兼容包装，避免直接改变默认语义导致旧调用误删。

### 4.3 P0-B：批次提交、水位线与幂等

仅调整“先保存、后推进水位线”的顺序不够：保存若吞异常，上层仍会认为成功。

建议为每个抽取批次生成稳定的 `batch_id`，由会话标识、实际消息 ID 集合及抽取版本确定；同一批次重试保持一致。消息处理位置与提取器版本分开保存，升级提示词不应自动重跑全部历史。

SQLite 增加 `memory_batches(batch_id PRIMARY KEY, conv, last_message_id, extractor_version, committed_at)`，并将本批事实、事件、画像变更、计数器及成功标记放入同一个事务。需重构现有各方法内部的 `commit()`：允许接收同一事务，不能在事务中调用会自行提交的旧方法。

```text
校验模型输出 → 构造变更集（不改共享缓存）
→ 事务写入全部变更 + 批次成功标记
→ 提交成功并刷新缓存
→ 推进现有 JSON 水位线
```

- 提交前失败：回滚，水位线不动；记录可重试失败。
- 提交后、JSON 水位线写入前崩溃：重启查到批次成功标记，只补水位线，不重复生成记忆。
- JSON 后端把批次标记和全部变更写入同一 payload。旧格式读取兼容，写入失败不可推进外部水位线。
- 提交成功后缓存刷新失败：使缓存失效并重新载入，不能继续对外提供半更新状态。
- 只读或校验失败不算成功；合法空结果可以记录已完成。异常输出不能当作空结果静默跳过。
- 将淘汰操作纳入明确的事务边界，或移到提交后的独立维护任务；不能因淘汰失败混淆“本批是否保存”。
- P1 中画像归纳可以异步完成，但抽取水位线推进前，必须已经提交画像证据和待处理任务。此后归纳失败由独立队列重试。

### 4.4 P0-C：提示词与上下文先做小范围对齐

1. `_extract()` 增加本批人物身份映射，注入这些人的现有画像摘要和同范围相关 facts；不要注入全库最近 20 条无关事实。
2. 在 schema、解析校验、`_apply_extraction()` 三处同步支持 `note`，并限制字段和字符串长度。P1 生命周期尚未实现前，不把临时状态自动写成永久 note。
3. 输出引用本批消息行号，由程序映射为持久消息 ID；检查引用属于本批、人物匹配，拒绝不存在的引用。身份不能仅由模型生成的姓名决定。
4. 明确区分本人自述、转述、玩笑、否定和纠正；旧画像只是上下文，不算新增证据。
5. 不要求模型输出固定条数。补充正反例，允许合法空结果；不要以“覆盖率”要求模型凑画像。
6. 此阶段只改善现有直接抽取；候选证据和定期归纳由 P1 实现。不要在候选机制尚未存在时放宽到自动保存所有推断。

### 4.5 P1：条目、证据和独立归纳任务

建议新增 `profile_items.py`（条目规则）和 `profile_jobs.py`（调度及重试），`memory.py` 保留入口和兼容渲染。存储 SQL 仍集中在 `memstore.py`，避免新模块自行打开第二套写连接。

**建议最小表结构：**

| 表 | 核心字段与约束 |
|---|---|
| `profile_items` | `id, uid_key, field, value, normalized_value, scope, visibility, status, source, first_seen, last_evidence_at, valid_until, revision, supersedes_id, import_batch_id` |
| `profile_evidence` | `id, uid_key, source_kind, source_ref, conv, observed_at, assertion_kind, minimal_excerpt, dedupe_key UNIQUE` |
| `profile_item_evidence` | `item_id, evidence_id`，联合唯一，关联双方外键 |
| `profile_jobs` | `id, uid_key, scope, input_revision, status, attempts, next_retry_at, lease_until, last_error`，同身份/范围/输入版本唯一 |
| `profile_tombstones` | `uid_key, scope, field, normalized_value, reason, created_at`，记录拒绝或撤回，阻止旧证据重建 |

实施时补齐 DDL、索引、外键和 schema 迁移版本。候选与正式画像使用同一张 `profile_items` 表的状态区分，不维护两份易失配的内容。多值偏好允许并存，不能给 `(uid_key, field)` 加唯一约束；同范围同语义有效条目应去重。

字段先支持 `love / dislike / habit / note`，`display` 仍属身份展示。职业、作息、临时状态可用条目的 `subtype` 扩展，不急于给原 profile 表增加大量列。`note` 每条表达一个含义，并能单独过期。

原 `profile` 表作为兼容投影，由有效条目生成；与条目状态变更在同一事务更新，或明确标记待重建版本。历史画像导入标记 `legacy`，不能伪造消息证据。新旧写入口都应通过统一服务，禁止双向独立修改。

**证据与升级规则：**

| 情况 | 默认处理 |
|---|---|
| 本人明确表达普通、稳定偏好 | 一条有效消息即可确认 |
| 本人明确要求记住某项普通属性 | 可确认，仍需核验身份、范围和来源 |
| 从多次行为推断习惯 | 候选；至少两次不同时间的独立证据，再判断是否足以归纳 |
| 他人转述、玩笑、反讽、身份不明 | 不自动确认；必要时留待核对候选 |
| 求职、考试准备等临时状态 | 独立条目，默认 30 天后停止展示；明确结束时间优先 |
| 本人明确纠正旧值 | 新值确认，旧值标记 `superseded`，保留关联 |
| 含糊矛盾 | 新值候选，旧值不被静默覆盖；待核对 |
| 人工删除或拒绝 | 写撤回记录；旧批次重跑不得自动恢复 |

状态建议为 `candidate / confirmed / rejected / superseded / revoked / expired`。人工来源不自动淘汰，但仍受有效期、用户删除和可见性限制。

同一消息被多次抽取、被多个 facts 引用或被模型反复改写，只算一份证据。证据去重键应包含来源标识和陈述身份，不要仅按文本去重，也不要把一条消息内两个不同偏好合成一个证据。模型自报置信度只作调试信息，不作为唯一升级阈值。

**归纳调用协议示意：**

```json
{
  "uid_key": "uid:示例用户",
  "input_revision": 7,
  "updates": [
    {"action": "add", "field": "love", "value": "喜欢某类音乐", "evidence_ids": [12, 18]},
    {"action": "replace", "item_id": 21, "field": "note", "value": "正在找工作", "evidence_ids": [23], "valid_until": "2026-11-21"}
  ]
}
```

程序校验 UID、字段、引用、作用域、目标条目归属及版本；模型不能指定任意库内证据或绕过撤回记录。最终状态由程序规则决定，模型只提出变更。

**调度与恢复：**

- 明确自述走快速确认；推断类每人累计 3 条新证据触发归纳，或有新增证据时每日补漏。无新证据不调用模型。
- 默认每人每范围每日最多一次后台归纳，手动重建和明确纠正不受这项后台配额阻塞；输入最多 30 条未处理证据，剩余证据保留队列，不直接丢弃。
- 同一 UID/范围串行归纳，调用模型时不持有数据库事务。返回后比较 `input_revision`，版本变化则重新排队，不覆盖新结果。
- 任务领取设置租约；进程退出后到期可重新领取。失败按 1、5、30 分钟退避，随后置为待人工检查并显示积压，不无限重试。
- 条目变更、兼容投影、已处理证据位置和任务完成状态同事务提交。归纳合法空结果也记进度；失败不推进。
- 提供独立配置开关 `profile_induction_enabled`，默认关闭；先离线验证再灰度。该开关只控制新归纳，不影响 P0 持久化修复。
- P0 维持两后端兼容；P1 先支持 SQLite。JSON 模式明确禁用归纳并提示能力限制，不能静默丢失条目元数据；回切 JSON 前先导出受支持投影并保留完整 SQLite 快照。

### 4.6 回填、渲染与人工入口

**回填可在 P0 后小规模恢复，也可在 P1 后完整导入：**

1. 使用 SQLite backup API 生成一致性快照，并验证可打开和 `PRAGMA integrity_check`。不要复制正在变化的 `.db` 单文件作为备份，也不要依次复制 WAL/SHM 假定得到同一时点。
2. 以 UID 分组，旧显示名不能唯一匹配时停在待核对清单；跨会话来源保留范围限制。
3. 从旧 JSON、facts 提取候选，报告新增、重复、冲突、过时、已撤回、身份不明及来源引用。关键词只用于召回，不能直接决定真实性。
4. dry-run 输出稳定导入计划、源快照标识及目标版本；应用前复查目标版本，发生变化则重新计算差异。
5. P0 阶段只导入经审核的明确条目，并另存导入清单与前后值；P1 阶段通过证据和条目服务写入，记录 `import_batch_id`。
6. 相同计划重跑不重复导入。撤销批次时只恢复该批次独占且此后未修改的条目；有后续修改则输出冲突，不能覆盖新数据。
7. 原 facts 保留，渲染时去重；旧 JSON 保留作历史凭据，不覆盖新库。

**渲染：**

- 先筛选权限/范围、确认状态、有效期，再按当前说话人、明确提及者、话题相关度选择。
- 使用总预算和每人预算，预算不足时允许跳过低相关人物；不强求所有人至少一行。
- 同义 facts 与画像优先保留当前有效、来源更明确的表达，关联来源用于排查。
- 可增加 `profile_recall_count / profile_budget`，先沿用当前预算作对照，再根据固定语料评估调整。

**人工入口：**

- 控制台增、改、删、确认候选、查看证据；请求携带条目版本，版本冲突提示刷新。
- 指令入口复用同一服务，不绕开持久化、权限、撤回和审计规则。
- “删除画像内容”应清理关联的敏感摘录；防恢复记录只保留最小必要标识，避免用历史记录变相永久保留被删除原文。

## 5. 实施拆分与发布指导

### 5.1 可独立评审的工作包

| 顺序 | 工作包 | 主要改动位置 | 完成条件 |
|---|---|---|---|
| 1 | P0-A 存储契约和原子归并 | `memstore.py`、`memory.py` | 两后端往返、失败回滚、归并故障注入通过 |
| 2 | P0-B 批次可靠提交 | 抽取入口、存储事务、水位线 | 崩溃后可重试，无丢失、无重复；失败指标可见 |
| 3 | P0-C 抽取对齐 | 提示词、schema、身份映射、解析 | note 全链路一致；来源可校验；固定语料无明显精确率退化 |
| 4 | 小范围存量恢复 | 拟新增回填脚本与报告 | dry-run、审核计划、备份、重复导入及撤销验证完成 |
| 5 | P1 条目与证据 | 数据迁移、拟新增条目服务 | 历史兼容、状态流转、范围过滤和撤回测试通过 |
| 6 | P1 独立归纳 | 拟新增任务模块与配置 | 重试、租约、版本冲突、限额和关闭开关有效 |
| 7 | P2 展示与人工管理 | `render_profile()`、控制台和指令实际路由 | 相关性、权限、编辑及删除验证通过 |

P0-A 可以先上线止损，但在 P0-B 完成前，不能宣称整条抽取链具备完整的故障恢复保证。估时应在事务边界和调用方审计后给出；不沿用原方案“P0 0.5～1 天”的估计。

### 5.2 开发与发布步骤

1. 搜索所有画像写入口及嵌套字典修改，列出自动抽取、归并、清空、迁移、载入清洗和人工入口；明确各自应采用 merge、replace 还是 clear。
2. 在 `验证/` 增加专用画像持久化与任务验证脚本，沿用现有 `_记忆验证.py` 的依赖隔离方式。测试仅使用临时目录和模型桩。
3. 先用脱敏数据副本验证 schema 迁移与回退，再对真实运行库做备份；记录备份路径、schema 版本和部署版本。
4. 发布 P0 后通过真实写入入口执行一条可识别测试画像，在独立连接中核查；安排受控重启后核对并清理测试数据。仅看到控制台内容不算验收。
5. P1 默认关闭归纳，先对固定数据运行仅出报告的模式，再对少量明确 UID/范围启用；对照观察失败数、积压、误判及调用量。
6. 上线失败先关闭新归纳任务，保留证据和队列。需要回退代码时，验证旧版可读当前 schema；不兼容时使用验证过的迁移/导出方案，禁止直接删除新表。
7. 全库恢复快照会丢失快照之后的变更，只用于明确安排的停写恢复；正常批次撤销优先走条目级补偿。

## 6. 验收用例与观测指标

### 6.1 必须通过的工程用例

| 用例 | 操作 | 预期 |
|---|---|---|
| 两后端往返 | 新增/修改/清空后关闭并重新打开 | 字段及删除状态一致 |
| 写入失败 | 注入提交失败、只读和 JSON 替换失败 | 返回失败；内存、磁盘保留旧值；水位线不动 |
| 归并中断 | 在目标更新和源删除之间注入异常 | 源目标均恢复到事务前状态 |
| 提交后崩溃 | 提交完成、推进外部水位线前退出 | 重启识别批次，只补进度、不重复写 |
| 幂等重试 | 同一批次、同一回填计划执行两次 | 条目数和独立证据数不增加 |
| 缓存一致性 | 写入后检查公开容器、原始缓存和独立连接 | 值相同；失败不出现内存假成功 |
| 空值与缺省 | merge 空列表、replace 空列表、未传字段 | 分别不新增、清空、保持原值 |
| 身份隔离 | 同名不同 UID，旧名多重匹配 | 不串画像，歧义留待核对 |
| 来源范围 | 同一 UID 有私聊和群聊证据 | 群聊渲染不泄漏私聊条目 |
| 纠正和过期 | 明确改口、到期、人工删除后再重建 | 旧值不进入 prompt，不被旧证据恢复 |
| 并发版本 | 慢归纳期间发生人工修改 | 旧结果不覆盖新值，任务重新评估 |
| 队列恢复 | 领取任务后退出、模型失败、合法空结果 | 租约恢复、失败退避、空结果正常完成 |
| 迁移与加载 | 旧库升级后重复启动、只读加载 | 不重复迁移，纯加载不意外写盘 |

上述用例是未来实施验收清单，**本次文档更新未执行这些测试**。新增功能完成后执行专用验证及受影响的既有记忆验证，再运行项目要求的检查。

### 6.2 抽取评估

固定至少 50 段脱敏聊天，标注人物、陈述类型、应提取条目、证据和范围；覆盖否定、玩笑、转述、多人同名、纠正、临时状态。旧/新提示词使用相同模型和参数，每段重复 3 次观察随机波动，记录提示词版本及输出。

- 精确率：正确确认条目 / 全部确认条目，初始目标 ≥90%。
- 召回率：正确提取条目 / 标注中应提取条目；要求相对旧版提升，首轮基线出来后再定绝对目标。
- 身份错配、越权渲染：固定用例必须为 0；不能用总平均精确率掩盖此类错误。
- 渲染相关命中：本轮应展示且有效的条目中，实际展示的比例，同时记录无关条目占比及预算。
- 按场景分别报告结果和样本数；小样本达标不代表线上总体保证。

### 6.3 运行指标

P0 即增加写入尝试/失败数、归并失败数、批次重试数、最近成功提交时间；P1 增加待处理任务数、最老任务年龄、失败任务数、证据到确认的延迟、版本冲突数、模型调用及 token 用量。日志记录 batch/job 标识和错误类别，避免输出完整私人聊天。

不再以“每人平均字段数”“最近 30 天必须更新”“展示全库 70%”“每周转化必须大于 0”作为硬门槛。无新证据时不应强行更新；稳定偏好长期有效不等于过时。画像覆盖率仅作为描述性指标，分母应限定为有可用画像证据的活跃人物，并注明统计范围。

## 7. 风险与边界

1. 默认不自动推断或保存敏感属性；明确要求记住的情况需遵守现有权限和可见性规则。候选池同样属于存储，不能绕过此限制。
2. 重复来源不等于独立证据，模型置信度不等于真实概率；确认规则必须由程序执行。
3. 归并、回填和重建都必须保留身份范围，不凭昵称猜测；历史数据来源不明时不自动提升可见性。
4. 模型费用不以未经测量的“成本很低”作保证；以实际调用次数、输入输出量和预算上限控制，达到上限保留队列。
5. 数据备份采用一致性备份机制；恢复时由程序管理连接和 WAL 状态，不手工拼接数据库与日志文件。
6. 当前本地目录不是可用的 Git 工作树；文档编辑可正常完成，后续代码实施需按实际版本管理方式保留可审查差异和回退版本。

## 8. 默认决策与后续调参项

| 问题 | 本方案默认决策 |
|---|---|
| 职业、作息是否立刻扩列 | 先用独立条目及 subtype，兼容展示到 note；临时条目必须有有效期 |
| 是否所有属性都需要两次证据 | 否；明确普通自述一次可确认，推断习惯需独立证据积累 |
| facts 回填后是否删除原记录 | 保留原 facts 及来源，prompt 去重 |
| 是否直接换更强模型 | 先用现有模型与严格 schema 建基线；有明确错误类别再做对照 |
| 敏感信息默认策略 | 不自动推断或保存；候选层同样适用 |
| JSON 后端范围 | P0 完整兼容，P1 归纳仅 SQLite；回切需保留完整新数据 |
| 新归纳初始参数 | 3 条新证据触发、最多 30 条/次、每人每范围每日一次后台归纳 |
| 临时状态有效期 | 无明确期限时初始 30 天，可按 subtype 配置；到期不主动猜测延长 |

参数是可调整起点，不是已验证最优值。实施不必等待全部参数确定：先完成可靠存储和可追溯数据模型，再通过固定语料及灰度结果调整。

## 10. 结论

机器人本身没有停，抽取任务也在跑；画像为空不是“最近没记”，而是：

1. **画像写入没有可靠落盘**，重启即丢，磁盘只剩空行；
2. **抽取把画像信息写进了 facts**，且没有从 facts 回补画像的通道；
3. 提示词、schema、现有画像上下文和渲染预算都在压低画像覆盖率。

实施方向是**把画像作为由可追溯消息证据归纳出的结论层**，历史 facts 是证据来源之一。先完成可靠写入、原子归并和批次恢复，再通过条目生命周期、独立归纳任务、存量回填和相关性渲染提高可用性。以第 5 节工作包和第 6 节验收清单作为实施入口；本文方案尚未落实为代码。
