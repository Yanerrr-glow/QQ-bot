## 1. 架构

```
   QQ 客户端
        │
        │  ① NapCat 把 QQ 协议翻译成 OneBot v11
        ▼
   NapCat  ──  ② WebSocket（正向 ws://127.0.0.1:6700 或反向）
        │
        ▼
   NoneBot2（本项目, Python 3.12）
        │   插件 plugins/ai_chat
        │  ③ 每条群消息落盘 → data/chatlog_<会话>.json（带已读/未读标记）
        │  ④ 被 @ 时：已读压缩成背景 + 未读原样呈现 → HTTPS
        ▼
   DeepSeek API  →  回复沿原路回到群里
        │
        └─ ⑤ 回复后把这些未读标记为已读，机器人自己的回复也落盘
```

**正向 WS 还是反向 WS？**

| | 正向 WS | 反向 WS |
|---|---|---|
| 谁监听端口 | NapCat 监听 6700 | NoneBot2 监听 8080 |
| NoneBot2 需要暴露端口 | 不需要 | 需要 |
| 配置复杂度 | 只改 NapCat 一处 | 两边都要配对，容易被防火墙拦 |

本地跑用正向最省事（本仓库默认）。放进容器时反向更稳 —— 同网络里 NapCat 的 WS 服务端
可能只监听 `127.0.0.1`，bot 容器连不上。见 [`deploy/README.md`](../deploy/README.md)。

## 2. 目录结构：模块与工具清单

```
.
├─ bot.py                        入口：init → 注册适配器 → 加载插件
├─ requirements.txt              依赖清单
├─ requirements-render.txt       渲染兜底（无头 Chromium）的额外依赖
├─ .env.example                  配置模板（真实配置写进 .env，不入库）
├─ Dockerfile                    Linux 容器镜像
├─ persona_base.txt              **底层人设**（它是谁）—— 只有你能改
├─ persona_forbidden.txt         **禁止事项**（铁律）—— 只有你能改
├─ persona_surface.txt           **表层人设**（怎么说话）—— 只有自动迭代会写
├─ data/                         运行时数据（不入库）
│   ├─ chatlog_<会话>.json       每会话一个，含已读/未读状态
│   ├─ chatlog_<会话>.archive.jsonl  超上限时挪过来的旧消息（归档，不删除）
│   ├─ memory.db                 长期记忆：人物画像 + 事实 + 群事件（SQLite）
│   ├─ memory_extract_state.json 记忆抽取水位线：每个会话抽到哪条了
│   ├─ msgindex.db               翻旧账：全量消息的词面倒排索引
│   ├─ session_summaries.json    会话轮次摘要：被丢弃的更早背景的回顾入口
│   ├─ settings.json             控制台改过的参数（优先级高于 .env）
│   ├─ stickers/                 表情包库：图片 + index.json
│   └─ bot.log                   启动脚本落盘的日志
├─ plugins/ai_chat/              插件本体（30 个模块）
├─ _工具链/                       本机与运维脚本
└─ deploy/                       服务器部署模板（Docker + NapCat + SearXNG）
```

### `plugins/ai_chat/` 各模块职责

| 模块 | 作用 |
|---|---|
| `__init__.py` | 三个入口：记录所有消息 / 被 @ 时回复 / 起后台任务 |

| `chatlog.py` | 落盘、会话切分、已读未读、预算压缩、溢出归档、增量取数 |

| `msgindex.py` | 翻旧账：全量消息的词面倒排索引与检索 |
| `summaries.py` | 会话摘要：切分点归纳、渲染进 prompt、按会话轮次淘汰 |
| `persona.py` | 人设三层：组装、冲突闸门、表层写入 |
| `persona_iter.py` | 人格自我迭代：定期反思 → 候选 → 过闸门 → 写表层 |
| `signals.py` | 人设信号账本：**只观察**用户说过的说话方式要求，不改人设 |
| `instructions.py` | 实时指令：斜杠解析 + 自然语言兜底 |
| `introspect.py` | 机制说明：把真实配置渲染成事实（主人全量 / 他人简版） |

| `stickers.py` | 表情包库：下载、去重、人格打分、随机取用 |
| `proactive.py` | 主动发言：定时掷骰 + 消息数触发 + 三重限流 |

| `search.py` | 联网搜索：多后端、限流、防注入渲染 |

| `fetch.py` | 读网页正文：受限抓取（防 SSRF / 限体积 / 超时） |
| `render.py` | 渲染兜底：HTTP 被反爬拒绝时用无头 Chromium 读 DOM |
| `mode.py` | 说话模式：按场合自动调整语气与长度 |
| `perceptual.py` | 感知层：消息的可量化特征 |
| `dsh_bridge.py` | `/dsh` 任务投递与取件（落盘 + 轮询，供本机 agent 消费） |
| `settings.py` | 可调参数（spec 表驱动 .env 默认值与 Web UI 表单） |
| `webui.py` | Web 控制台（FastAPI 路由 + 单页前端） |
| `config.py` | 不可调项与路径（含"当前时间"注入、人设来源） |

### `_工具链/` 各脚本职责与适用性

先说「适用」这一列为什么存在：这里的工具比框架本体还多，但**不是每一个都跟你有关**。
第一次读这个仓库时，先按这一列筛一遍，能省掉大量"这个到底能不能用"的试错。

> **`persona_traits.json` 不随本仓库分发。** 这份特质注册表的 `channels` /
> `observed_bad_examples` 里含**线上真实对话原话**，发出来等于替群友公开聊天记录；
> 作者一侧的导出脚本把它整份列在「有意不同」里跳过了。**运行时不需要它** ——
> `persona.py` / `behavior.py` 都有内置回退，机器人照常跑；但两份巡检脚本需要：
> `_人设结构检查.py` 会直接报「找不到 persona_traits.json」并以**退出码 1** 结束，
> **这是有意的**（缺文件就该报错，不该报绿）。想用它们，按 `persona.py` /
> `behavior.py` 实际读取的字段自己写一份即可 —— 字段含义见 `_人设结构检查.py`
> 开头列的三张清单。`离线验证_桩.py` 同样依赖它，但那份会**自动跳过**注册表相关的
> 17 项并在结尾写明「跳过 N 组」，所以缺注册表时它仍跑得完（990 项通过、退出码 0）。

> **摘要的缺口**：摘要的触发点是**会话切分**，所以只有"功能上线之后新结束的那一轮"
> 才会被总结；上线之前盘上已有的轮次永远不会被总结，而这个缺口不会自愈。
> `_回填摘要.py` 就是补它的（先 `--dry-run` 看缺口，再去掉跑）：
>
> ```bash
> docker exec -w /app ai-chat-bot python /app/_工具链/_回填摘要.py --dry-run
> docker exec -w /app ai-chat-bot python /app/_工具链/_回填摘要.py --max-calls 100
> ```
>
> **画像重复**：控制台「人物画像」里可能出现好几个本该是同一个人的条目，甚至包括
> 机器**自己**的昵称。三个成因都在写入路径上（代码侧已修）：模型给人设角色写画像、
> 名字变体（`小明 ` 带了尾空格）解不出 uid、键被截到 24 字后长昵称分裂。
> 存量数据用这个脚本过一遍（**先 dry-run**，它会自动备份 `memory.db`）：
>
> ```bash
> docker exec -w /app ai-chat-bot python /app/_工具链/_修复画像重复.py --dry-run
> docker exec -w /app ai-chat-bot python /app/_工具链/_修复画像重复.py
> ```
>
> 它只动 `profile` 表，**facts / events 一条都不碰**；拿不准的条目（两个真同名的人之类）
> 只列出来给你判断，不擅自合并。
>
> **套件输出为什么值得单独一个脚本**：`离线验证_桩.py` 有 800 多条断言、上万行输出，
> 而控制台只保留尾部 —— 于是"到底过没过、挂在哪几条"常常看不见。
> `_跑桩验证.py` 把完整输出写进 `_selftest_full.log`，之后随便 grep。

> **两份离线验证的分工**：`离线验证.py` 查"装得起来吗"（起一遍驱动、加载整个插件包）；
> `离线验证_桩.py` 查"算得对不对"（无依赖也能跑）。改完代码两份都该跑一遍。
>
> **PDF 那三个脚本的分工**：`_PDF读取验证.py` 在本机跑（只要 pymupdf，验纯逻辑）；
> `PDF端到端验证.py` **必须在容器里跑** —— 本机通常没装 OCR，扫描版那条路只有容器里能走通：
>
> ```bash
> docker exec -e PYTHONIOENCODING=utf-8 ai-chat-bot \
>     python /app/_工具链/PDF端到端验证.py /tmp/某份.pdf
> ```

## 3. 配置项速查

完整清单见 `.env.example`（每一项都有注释）与 `plugins/ai_chat/settings.py` 的 `_SPECS` 表。

> `settings.py` 里 `_SPECS` 登记的**可调参数**，实际入口是 Web 控制台
> （<http://127.0.0.1:8080/ai/>）：改完即时生效，值存 `data/settings.json`，
> **优先级高于 `.env`**。`.env` 里的同名项只是初始默认值。

### 必填

| 变量 | 默认 | 说明 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 空 | **必填**，为空时机器人会在群里提示未配置 |
| `AI_CHAT_MASTER_QQ` | 空 | 主人的 QQ 号。**留空 = 没有主人**，定时问候与 `/dsh` 不生效 |

### 模型

| 变量 | 默认 | 说明 |
|---|---|---|
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | 换中转 / 自建服务只改这里 |
| `DEEPSEEK_MODEL` | `deepseek-flash` | 也可在控制台热切换 |
| `AI_CHAT_TIMEOUT` | `60` | 单次请求超时（秒） |
| `AI_CHAT_MAX_CONCURRENCY` | `4` | 同时处理的最大提问数 |

### 触发与上下文

| 变量 | 默认 | 说明 |
|---|---|---|
| `ONEBOT_WS_URLS` | `["ws://127.0.0.1:6700"]` | 必须与 NapCat 监听端口一致 |
| `AI_CHAT_PREFIX` | 空 | 留空 = 只靠 @ 触发；填 `/ai ` 则同时支持前缀 |
| `AI_CHAT_GROUP_WHITELIST` | `[]` | 留空 = 所有群响应 |
| `AI_CHAT_SESSION_GAP` | `300` | 会话切分间隔（秒）。**这是省 token 的主开关** |
| `AI_CHAT_READ_BUDGET` | `2000` | 已读背景的字符预算 |
| `AI_CHAT_MSG_CLIP` | `120` | 单条消息截断长度（0 = 不截断） |
| `AI_CHAT_RECORD_ALL` | `true` | 是否记录所有群消息（含没 @ 它的闲聊） |
| `AI_CHAT_MAX_MESSAGES` | `0` | 单会话最大条数。**超出是「归档」不是删除** |

### 人格

| 变量 | 默认 | 说明 |
|---|---|---|
| `AI_CHAT_PERSONA_FILE` | `persona_base.txt` | 底层人设。写成**空串** = 关掉文件读取 |
| `AI_CHAT_FORBIDDEN_FILE` | `persona_forbidden.txt` | 禁止事项。自动迭代碰到它直接丢弃 |
| `AI_CHAT_SURFACE_FILE` | `persona_surface.txt` | 表层人设。**唯一会被自动迭代写入的一层** |
| `AI_CHAT_BOT_NAME` | `鲸鱼娘` | 机器人在聊天记录里的显示名，**必须与人设角色名一致** |
| `AI_CHAT_SYSTEM_PROMPT` | 见模板 | 只在上面的人设文件缺失 / 被关掉时生效 |

### 长期记忆

| 变量 | 默认 | 说明 |
|---|---|---|
| `AI_CHAT_MEMORY_ENABLED` | `true` | 总开关。关掉退回"只看最近记录" |
| `AI_CHAT_MEMORY_RECALL_COUNT` | `6` | 每次回复最多带几条记忆进 prompt |
| `AI_CHAT_MEMORY_MIN_SCORE` | `0.18` | 入选分数线 |

## 4. prompt 是怎么组装的

固定八段，**顺序就是优先级**（可缓存的部分在前，每轮变化的部分在后）：

```
system:
  ① 人格三层（底色 → 铁律 → 表层）
  ② 运行时风格要求      data/persona_directives.json（聊天里 /风格 改的）
  ③ 当前时间
  ④ 聊天记录的读法      **由代码保证**（context.record_legend）
  ⑤ 长期记忆           相关的事实 + 人物画像
  ⑥ 你自己的机制事实      只在真被问到时才注入（避免凭空编）

user:
  ⑦ 更早的聊天记录（已读过，压缩）＋ 刚才的新发言（原样）＋ 引用 + 文件 + 图片
  ⑧ 本次要回应的发言
```

第 ⑥ 段是**按需的**：问「你的图片机制是什么」才生成，平时一个 token 都不花 ——
这也是"机制说明不是幻觉"的实现方式。

## 6. 这个仓库与它的"活项目"是什么关系

本仓库是一份**脱敏后的对外副本**，源自在真实群里跑着的那个项目。两者由作者一侧的
两个脚本保持对齐（都在**活项目**的 `_工具链\` 下，**本仓库没有它们**），判据不是
"逐字节相同"，而是：

> 活项目的那份文本，经**同一套脱敏映射**变换之后，应当与这里逐字符相同
> —— 除非它列在「有意不同」清单中（每一条都写了理由：对外重写过的文档、
> 含线上真实数据的分析记录、特质注册表与导出脚本自身……）。

**这两个脚本为什么不随仓库分发**：核对脚本里写着「真实值 → 占位值」的映射表 ——
表里就是真实的群号与群友昵称，发出来等于把要保护的东西一起发了。

所以这一节是**给维护者看的**，不是让你在本仓库里跑的命令：

```powershell
# 在**活项目**里跑（本仓库没有这两个脚本）
& '.\_工具链\_导出开源版.ps1'        # 生成 / 更新本副本
& '.\_工具链\_核对脱敏对齐.ps1'      # 退出码 0 = 对齐
```

核对会报三类真问题：副本缺失（忘了同步）、副本多余（在这里单方面改了没回流）、
内容有差异（既不在「有意不同」清单里、脱敏后也对不上），并直接指出第一处不同的行。
